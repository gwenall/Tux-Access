# Language and Linux packaging recommendation

Research date: 15 October 2026. This is a proposed release strategy, not a claim that the packages or additional distributions have passed testing.

## Decision

Keep the working Python/PySide6 application through the first polished release. Ship a versioned application directory containing CPython, the launcher, PySide6/Qt and its selected plugins. Wrap that directory in an Arch package first, then `.deb` and `.rpm` packages. Offer a portable tar archive and subsequently an AppImage from the same application payload. Keep Wine runtimes and yabridge as independently versioned, qualified components. An incremental Rust backend is a useful later option; a full GUI rewrite does not presently solve the hardest compatibility problems.

The launcher orchestrates account HTTP requests, verified downloads, filesystem transactions and subprocesses. DSP runs in NI's native libraries or Windows binaries through Wine/yabridge, which is a separate C++ bridge. Python is therefore not on the audio processing path. Current source has Python 3.10+, PySide6 `>=6.8,<7`, user-owned Wine prefixes, an Arch-only native installer and a system-browser OAuth callback. The broader dependency ranges suit development; releases need exact versions and hashes.

## Language choices

| Choice | Benefit for this project | Cost and recommendation |
| --- | --- | --- |
| Python + bundled interpreter + PySide6 | Preserves tested account/download/UI behavior; users do not install Python or pip dependencies; Qt already supports native desktop widgets. | Runtime size and dependency patching become release responsibilities. Lowest disruption; recommended now. |
| Rust backend + existing PySide6 GUI | Strong typed installation plans, cancellation, concurrency and ownership; a small backend executable can eventually replace CPython for CLI work. | Two languages and a protocol must be maintained; GUI still needs CPython/Qt. Moderate to substantial work; migrate only after stable behavior and parity tests. |
| Full Rust GUI | Eventually removes Python deployment and can consolidate orchestration. | Rebuilds widgets, accessibility, background jobs, login and error handling. Highest change risk. Qt bindings retain Qt ABI requirements; another toolkit brings its own graphics dependencies. Tauri also uses a web frontend and Linux WebKitGTK, so it is not a dependency-free Rust desktop. Defer. |

Qt provides `pyside6-deploy`, a Nuitka-based compiler/deployer that links libpython and supports a standalone directory. Use that explicit mode as the first packaging trial, with PyInstaller `onedir` as a fallback if the actual source or baseline exposes a blocker. Freeze after clean-environment tests; compilation alone does not prove compatibility. [Qt deployment tool](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html), [Tauri prerequisites](https://tauri.app/start/prerequisites/).

For a later Rust transition, start with a separate `native-access-backend` process and a versioned JSON request/event protocol over private pipes or Unix sockets. Port archive inspection, install transactions, download workers and runtime inventory in bounded steps. Preserve Python implementations as parity references until the same cancellation, rollback, auth and integrity tests pass. Keep secrets out of argv/logs and UI events. A separate process avoids adding a Python/Rust extension ABI to the first migration.

## Compatibility baseline

Propose **x86-64, glibc 2.34+, with Enterprise Linux 9 as the oldest release-build environment**. First runtime targets are current Arch, Ubuntu 22.04/24.04 and EL9; add newer Ubuntu/EL releases and Debian 12+ after actual qualification. This baseline is a practical choice for maintained Qt binaries and enterprise systems, not a promise that every glibc-compatible distro works.

The current official PySide6 Essentials 6.12.0 **x86-64** wheel is `manylinux_2_34`; its **ARM64** wheel is `manylinux_2_39`. Do not infer the floor from the ARM wheel or from Qt Online Installer builds. EL9 supplies glibc 2.34. Audit the entire frozen payload, including CPython, ZeroMQ, Qt plugins, C++ runtime and helper tools for symbol requirements; a manylinux tag on one wheel does not qualify the application. [PySide6 release files](https://pypi.org/project/PySide6-Essentials/6.12.0/), [RHEL9 toolchain](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/9.0_release_notes/overview), [Qt Linux requirements](https://doc.qt.io/qt-6/linux.html).

Build on the chosen oldest environment, then test newer targets. PyInstaller explicitly does not bundle glibc, and AppImage likewise requires an old-enough build plus testing of target systems. Also inspect `GLIBCXX` and `CXXABI` requirements. Do not globally replace system glibc, libstdc++ or graphics drivers. [PyInstaller Linux compatibility](https://pyinstaller.org/en/stable/usage.html), [AppImage build practices](https://docs.appimage.org/reference/best-practices.html).

Compile project-owned binaries without `-march=native` or an unnecessary AVX requirement. Audit bundled dependencies' instruction requirements. Kontakt's present backend requires AVX and the VM needed working XSAVE/OSXSAVE; keep that as a **product** preflight, independently from launcher startup. AVX2 must not be asserted without a requirement or exact-product evidence. x86-64 packaging cannot turn these existing NI x86 binaries into native ARM applications. Treat ARM, Alpine/musl and NixOS as separate future projects. A statically linked Rust/musl CLI may reduce that CLI's libc dependencies, but cannot remove Qt, Wine, the DAW or NI ELF ABI requirements. [Rust runtime linkage](https://doc.rust-lang.org/stable/reference/linkage.html).

The operating system also has a CPU floor: RHEL9 uses x86-64-v2; RHEL10 requires x86-64-v3. Building on EL9 does not automatically produce a first-generation x86-64 binary: explicitly select compiler flags and audit every bundled dependency. If generic x86-64 cannot be established, publish the measured launcher CPU floor. Do not move the common build to EL10 merely because it is newer. [RHEL9 instruction baseline](https://developers.redhat.com/blog/2021/01/05/building-red-hat-enterprise-linux-9-for-the-x86-64-v2-microarchitecture-level), [RHEL10 architectures](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/considerations_in_adopting_rhel_10/architectures).

Target EL9/EL10 and CentOS Stream, Rocky/Alma equivalents after testing, rather than reviving CentOS Linux 7/8 or Stream 8, whose upstream lifecycles have ended. Do not assume Fedora and openSUSE can share all RPM dependency names, paths and policies. [CentOS lifecycle](https://www.centos.org/cl-vs-cs/).

## Package formats and host integration

| Format | Role and limits |
| --- | --- |
| Arch `.pkg.tar.zst` | Primary supported release. Install desktop entry, URI handler, optional narrowly scoped helper and dependency metadata; pacman owns updates/removal. A source/system-Python PKGBUILD can remain a developer/community option. |
| Debian/Ubuntu `.deb` | Same bundled launcher payload with apt integration and distribution-specific dependency mapping. Build/install/remove tests must cover each advertised base. Do not execute NI's old Debian maintainer scripts blindly. |
| EL/Fedora/openSUSE `.rpm` | RPM wrapper with separate specs or conditionals for actual dependency names, paths and SELinux/desktop behavior. One RPM file is not automatically universal. |
| Portable `.tar.zst` directory | Earliest distribution-neutral fallback, no FUSE requirement; a user-local setup action can register desktop/URI integration. Easier to diagnose; updates and integration need project tooling. |
| AppImage | Useful secondary launcher delivery once the directory works. Bundle application libraries, keep prefixes/content outside the read-only image, test FUSE and extract-and-run paths. Install the callback through a stable user-local launcher path; a moved image must not strand the URI handler. It does not contain or magically export DAW plugins. |
| Flatpak | Defer for the complete installer. Useful later for a sandboxed catalog/download UI or with a separately installed, constrained host service. Host DAWs need real stable plugin paths; Wine prefixes and sample libraries need persistent external locations; native package installation needs a host mechanism. The current private callback socket and user-local `.desktop` registration need explicit adaptation. |

Use normal packaging tools for public launcher releases: `makepkg`/PKGBUILD, debhelper tooling and `rpmbuild`. This is distinct from the current `arch_package.py`, which creates **local NI product packages** from a user's checksum-verified download. Never put NI software, artwork, activation data or licenses in the launcher's release archives. [Arch packaging](https://man.archlinux.org/man/core/pacman/PKGBUILD.5.en), [Debian packaging manuals](https://www.debian.org/doc/devel-manuals), [RPM specs](https://rpm.org/docs/4.20.x/manual/spec.html).

Flatpak portals can open the external browser, but incoming `native-access://authorize` delivery and the live private socket must be tested across the host/sandbox boundary. `/usr` and other reserved host paths cannot simply become writable through a filesystem permission. `flatpak-spawn --host` explicitly runs outside the sandbox and needs a D-Bus permission; broad home/host/system-bus permissions are not an appropriate shortcut. Prefer portal-selected directories and a small host API if Flatpak is later justified. These constraints make deferral a project-specific engineering judgment. [Flatpak permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html), [host spawning](https://docs.flatpak.org/en/latest/flatpak-command-reference.html#flatpak-spawn).

The frozen build must update OAuth invocation: `oauth_browser.py` currently generates `sys.executable launcher.py --oauth-callback %u`; a frozen executable should dispatch its own callback mode through a stable entrypoint. Keep the private runtime socket, state, expiry and PKCE validation. Sanitize inherited bundle library and Qt plugin environment before launching the system browser, Wine, package manager or DAW, so those programs do not accidentally load the launcher's Qt/OpenSSL libraries.

Bundle the Qt platform plugins actually used (Wayland and xcb), image/font support and translations required by the UI; test their native dependencies rather than copying every Qt module. Avoid adding WebEngine when sign-in already uses the system browser. Install application files separately from user configuration, runtime prefixes, sample content and DAW plugin directories; upgrades must preserve the latter.

Run the GUI, browser callback, downloads and Wine as the user. Request system authentication only for the specific package transaction. A packaged privileged helper must validate an allowlisted product, manifest, paths and digests itself, stage immutable root-owned inputs and expose fixed actions rather than arbitrary commands. Do not grant the desktop blanket passwordless package-manager access. Polkit supports declaring individual actions and using the desktop's authentication agent. [Polkit architecture/actions](https://polkit.pages.freedesktop.org/polkit/polkit.8.html).

## Runtime versions, security and ABI ownership

Keep versioned runtime directories and a tested manifest containing launcher/Python/Qt versions, Wine build and matching wineserver, yabridge commit/build, architecture, hashes, licenses and dependency inventory. Wine 11.19/new WoW64 and Kontakt 8.9.0 are the present standalone evidence; yabridge development commit `b580a9f7` is pending bridge qualification. The current `>=11.19` check correctly warns for unqualified versions, but a polished automatic mode should select an exact qualified runtime. Offer explicit system-Wine/manual overrides with diagnostics.

Qualify Wine and yabridge together, including the same Wine host architecture and DAW environment. yabridge documents prefix detection and `WINELOADER` selection; the DAW's plugin process must receive the selected runtime configuration even when launched outside this launcher. Do not assume the GUI's PATH settings propagate to an independently started DAW. [Upstream yabridge configuration](https://github.com/robbert-vdh/yabridge#using-different-wine-versions).

Apply updates through signed releases/repositories, retain the previous runtime, and migrate/test a copy of a prefix before publishing an upgrade. Runtime pinning buys reproducibility, not permanent security: schedule dependency reviews, ship fixes, and requalify the affected product/host combination. Bundled Qt/Python need our updates; system dependencies need the distro's. Include dependency notices and source/relinking materials required by the actual Qt/PySide license choice; the project's MIT label does not cover them. [Qt licensing](https://doc.qt.io/qt-6/licensing.html).

Keep OpenSSL 1.1/Xerces 3.2 confined to the legacy product compatibility directory. Never use them for launcher HTTPS or add them to global loader configuration. OpenSSL 1.1.1 ended public upstream support in September 2023; the private directory does not make it patched or secure. RPATH also is not a process-security boundary: a host may load several plugins with overlapping ABIs. Track provenance/hashes and test coexistence; prefer maintained ABI-compatible fixes where available, and expose unsupported legacy products honestly. [OpenSSL lifecycle](https://openssl-library.org/post/2023-09-11-eol-111/).

## Phased delivery and acceptance checks

1. **Arch polished PoC:** finish managed-install/UI integration and VST3 validation; pin dependencies; package the launcher directory; exercise installed entrypoints and browser callback from a clean user account. This is moderate packaging/integration work without a language migration.
2. **Common release payload:** build on EL9/glibc 2.34; wrap as Arch, `.deb`, EL `.rpm` and portable tar; test current Arch, Ubuntu 22.04/24.04 and EL9/10 GNOME/KDE X11/Wayland as advertised. Expand Debian/Fedora/openSUSE only after their matrix passes. Multiple package adapters and VM/physical audio testing are substantial ongoing work.
3. **Portable polish:** create AppImage from that payload, verify stable callback integration, update/rollback and FUSE fallback. Treat installation locations, external content disks and manual runtime choices as normal settings.
4. **Optional Rust backend:** port one verified subsystem at a time after the protocol and workflows settle. Reassess a GUI rewrite or Flatpak host service only for demonstrated benefits.

CI should build a pinned x86-64 payload on the baseline, audit every ELF's symbol/instruction dependencies, and produce native wrappers in distribution build environments. Release smoke tests must use the installed/frozen application, not a checkout: no system Python/PySide dependency, no accidental imports from cwd, GUI launch on X11/Wayland, system-browser OAuth round trip, catalog and verified downloads, cancelled/failed install rollback, update/removal, denied Polkit authentication, paths with spaces, symlink rejection and unprivileged Wine prefix operation.

Audio gates are separate: native discovery/editor/DSP for each product; Kontakt standalone demo sound; yabridge VST3 discovery, GUI embedding, MIDI and finite nonzero DSP in an actual host; repeated sessions and measured latency/underruns on physical hardware. Current standalone loopback sound is evidence for that experiment, not activation, bridge or real-time qualification. Supported distributions, products and hosts must be named with tested versions. No language or container format can establish those results by itself.
