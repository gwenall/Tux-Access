Native Access account flow findings — 2026-10-14

Later parent investigation update: a local auth0_access_token_request was made
against the already-running user session. The returned token was held only in
process memory to corroborate two read-only NI account API routes. No token
value was printed/persisted and no fresh login/logout operation was made.
The account-products endpoint and download-metadata endpoint returned HTTP200;
details are in protocol-findings.txt version0.3 update. This verifies a current
session's direct API access, not a fresh Linux login or token refresh.
Native HTTPS auth transport and refresh preparation are now implemented in
auth_transport.py. Earlier observations below describe the narrower static
investigation at the time they were recorded.

Scope: static installed application evidence only. No existing account token
was queried, no authentication network request was sent, and no account or
daemon authentication state was changed in this investigation.

Independent implementation
outputs/native-access-linux/account_auth.py uses Python standard library.
It generates/verifies S256 PKCE, builds observed authorize parameters,
validates exact callback targets and mandatory state, and prepares observed
daemon login data without sending it. Optional exchange_code accepts an
explicit transport callable and constructs a standards-based authorization
code POST to the observed /oauth/token candidate endpoint. No default network
transport is present; direct HTTP exchange remains unverified NI behavior.
The caller-supplied transport must verify TLS, reject redirects, bound response
size, and avoid credential logging. Functions do not print or persist secrets.
OAuth state is an independent security design decision; NI redirect-handler
state preservation is unverified, so end-to-end login is not claimed.

Five tests passed in work/test_account_auth.py: RFC 7636 Appendix B test vector,
mock HTTP provider exchanges tied to authorization challenge, untrusted or
ambiguous callbacks rejected, invalid auth origin blocked before transport,
provider errors redacted. Reference: https://www.rfc-editor.org/rfc/rfc7636

Remaining gaps
No observed successful fresh login or direct HTTP token exchange; no proof
the production public client accepts Linux or alternate redirect registration.
No refresh token implementation or persistence; no NI daemon Linux equivalent.
No verified device polling, account catalog HTTP schema, installation entitlement
or license transport. Browser callback integration and user-owned session login
must be tested explicitly before describing account support as functional.
