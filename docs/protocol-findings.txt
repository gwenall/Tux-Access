Observed static wire mapping
Protocol version 8.1.4: constant at character offset 317120.
Envelope encoder at offset 244418; header at 242174; version at 243278.
Envelope field 1 is header, containing field 1 protocol version and optional
field 2 uint64 task ID (omitted/zero in the inspected request construction).
Protocol version fields 1, 2, 3 are uint32 major, minor, micro.
Envelope field 2 is error response: field1 enum integer, field2 UTF-8 message.
Envelope field 3 is empty success response.

Read-only request pairs (request mapping at offset 319691):
daemonPingRequest field7, empty -> successResponse field3, empty.
daemonVersionRequest field71, empty -> daemonVersionResponse field72.
knownProductsRequest field47, empty -> knownProductsResponse field48.
All are protobuf wire type2 (length-delimited embedded messages).
Daemon version fields: 1 major uint32, 2 minor uint32, 3 micro uint32,
4 build UTF-8 string (decoder at offset 231778).
Known-products response field1 is repeated KnownProduct message (189278).
KnownProduct encoder/decoder begins at 174076. Implemented presentation subset:
1 upid string; 2 isPlayer bool; 3 title string; 4 installedVersion message;
5 targetVersion message; 6 installedSize uint64; 7 installed bool;
8 updateable bool; 11 activationState enum integer; 12 isOwned bool;
13 targetSize uint64; 14 isLocatable bool; 15 isInstallable bool;
17 installationSource enum integer; 19 type enum integer;
20 isUninstallable bool; 25 company string; 26 vendor string;
28 platforms repeated string. Version submessages are major/minor/micro fields
1/2/3 uint32. Additional complex product fields remain unimplemented and are
ignored at protobuf framing level; the result is not a complete schema.

Request transport addresses are observed in constructor at 339522:
send tcp://127.0.0.1:5146; event subscription tcp://127.0.0.1:5563.
The Python implementation uses ZeroMQ REQ with one binary protobuf frame.
REQ framing was initially a transport candidate, then verified against the
running Windows daemon by the parent investigator with pyzmq 27.2.0.

Implementation and validation
outputs/native-access-linux/ntk_protocol.py independently implements bounded
protobuf parsing, three allowlisted request encoders, response decoding, and
NtkClient(endpoint='tcp://127.0.0.1:5146', timeout_ms=1500), methods ping(),
version(), known_products(), close(). Optional dependency pyzmq; codecs use
Python standard library alone. Only loopback TCP endpoints are accepted.
Per-request sockets avoid reusing a REQ socket after timeout. Reply size 32 MiB.
Five unittest cases passed in work/test_ntk_protocol.py: reference request
bytes, realistic response shapes, malformed wire/bounds, daemon errors and
major-version mismatch, unsigned integer limits.

Unknowns and portability limits
No native Linux NTK daemon was found or executed. Linux NTK compatibility,
transport on Linux, authentication portability, installation mechanisms,
events, and complete product metadata remain unverified. A Linux launcher
can use these probes only when a compatible local daemon actually exists.
Windows runtime success does not establish Linux support. Static protocol
constants are specific to the inspected Native Access version and may change.
